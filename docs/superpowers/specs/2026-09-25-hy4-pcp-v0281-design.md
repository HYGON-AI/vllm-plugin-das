# Hy4 PCP on v0.28.1-dev: Design

## Purpose and baseline

Restore and extend Hy4 prefill context parallelism (PCP) on HCU Model Runner
V2 without changing the validated TP/DP/EP path in PR #152. This is a
stacked follow-up MR based on PR #152 commit `1b51a2b`; it will initially
target `feat/hy4-v0281-alignment` and can be retargeted to `v0.28.1-dev`
after that MR merges.

The paired v0.25.1 HCU stack demonstrated two eight-card eager topologies:
TP4/PCP2/EP8 with built-in MTP up to two tokens, and PP2/TP1/PCP4/EP4
with DeepEP high-throughput, DeepGEMM, FP8 E4M3 KV and MTP2. The latter
scored HumanEval-32 32/32 both without MTP and with MTP2. Those results are
reference evidence, not proof on the target v0.28.1 runtime.

## Supported configurations

The first target is TP4/PCP2/EP8/PP1/DP1/DCP1 on eight HCUs, eager,
`FLASHMLA_SPARSE`, with target-only and built-in MTP1–3. The historical
PP2/TP1/PCP4/EP4/DCP1 topology is a second target, eager, FP8 E4M3 KV,
DeepEP high-throughput plus DeepGEMM, with target-only and MTP2. Its PP
partition must start stage 2 on a full indexer layer (`41,37` for the
checkpoint used here). Other PCP topologies stay fail-closed unless they
receive their own tests and live gate.

The plugin config gate restricts topology and structural prerequisites, not
the independent KV dtype, all-to-all and MoE selectors. The PP2 accuracy claim
is limited to the FP8 E4M3/DeepEP high-throughput/DeepGEMM command above;
other backend selections may pass config validation but are not validated by
this MR. Do not describe gate acceptance as an accuracy guarantee.

PCP+CUDA Graph is not a deliverable of this MR. The installed target vLLM
explicitly rejects sparse MLA PCP when graph mode is not `NONE`; `--enforce-eager`
is required for the supported PCP launches. DCP>1 together with PCP>1,
DP>1, unsupported speculative methods, LoRA, multimodal input, KV offload,
and P/D disaggregation remain unsupported. These must fail during config
validation, before loading weights. PCP1 behavior must remain unchanged.

## Runtime design

1. Extend the HCU PCP configuration contract only for
   `HYV4ForCausalLM` and the exact topologies above. Keep the existing
   GLM-5.2/GQA contract intact. Use the official MRV2 `pcp_manager_cls`
   extension point and the existing `HcuPCPManager`; do not copy the
   v0.25.1 runner or bypass unrelated upstream validation by bytecode tests.
2. Permit Hy4's sink-capable sparse FlashMLA implementation to consume PCP
   metadata only after its local-query, full-cache and LSE contracts are
   covered. Short prefill remains on sparse MQA so every token applies the
   learnable sink. Keep the official KV allocation and HCU native writer.
3. Separate attention-kernel phase from KV ownership. The manager's
   rank-local virtual padding and per-segment ownership must drive latent
   KV and indexer cache gathers. Replicated decode or MTP verification rows
   must not be gathered a second time; partitioned prefill rows must retain
   rank-ordered slots. Sparse indexer top-k and shared producer/consumer
   buffers remain local to the correct token rows.
4. Preserve upstream's final-stage ordinary PCP sampling restore. In the MTP path,
   restore the saved global target batch exactly once and keep the draft's
   replicated ownership through each metadata rebuild. Do not replace the
   official PP broadcast; for PP2, non-final stages restore the saved global
   batch without a hidden-state collective, while only the final stage
   gathers hidden states for sampling.
5. Preserve DeepEP's current all-to-all selection and the selected MoE
   backend. Do not restore the v0.25.1 communicator `use_all2all` monkey
   patch. Profile success, backend selection and MTP acceptance are
   supporting evidence, not accuracy evidence.

## Alternatives considered

Copying the old PCP runner would be smaller initially but duplicates current
MRV2 partition/restore ownership and risks incorrect MTP metadata. Modifying
the target vLLM to enable sparse-PCP CUDA Graph would require a paired wheel,
graph-safe metadata and collective design, and a separate accuracy gate.
The narrow current-MRV2 adapter above is preferred for the eager baseline.

## Verification and release boundary

Use test-first changes for config acceptance/rejection, sparse sink + LSE,
slot order, replicated decode versus partitioned prefill, MTP unequal draft
counts, PP sampling, and unchanged PCP1 behavior. Run every changed test file,
the full Hy4 and PCP source suites, and the repository suite; report all
failures, including pre-existing ones.

Live validation starts with TP4/PCP2 target-only, then MTP1/2, then MTP3;
it includes concurrent requests with unequal draft acceptance and delayed
decode-plus-fresh/continued-prefill mixtures. The PP2/PCP4 historical
topology then requires short and long prompt checks plus HumanEval-32 for
target-only and MTP2 using the same evaluation protocol as v0.25.1. Require
actual HCU backend/manager markers, request finish reasons, FP8 KV cache
selection, draft acceptance, and complete functional scores. Run from an
isolated plugin wheel matched to a recorded vLLM wheel/source SHA. Do not
claim PCP Graph, PCP+DCP, or untested topologies from these gates. Record
the exact service commands and evidence in the new MR and update the local
upgrade skill only after an evidence-backed gate.
